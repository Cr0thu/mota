\begin{abstract}
Magic Tower is a deterministic single-agent role-playing puzzle in which the
agent must allocate health, attack, defense, keys, and money across many
irreversible interactions.  The first-ten-floor task studied here starts after
the early thief event and terminates when the Floor-10 skeleton captain is
defeated.  The task is fully observable and rule-defined, but naive
reinforcement learning rarely receives a useful terminal signal.  We therefore
separate three experimental lines: prompt-guided route discovery as diagnostic
data, expert-trajectory potential learning from the hp403 route, and a
warm-started AlphaZero-style policy/value line based on multiple successful
routes.  The hp403 trajectory is not used as a behavior-cloning target in the
pure line; it is used only to learn a potential function for shaping
\(\gamma\Phi(s')-\Phi(s)\).  The newest 4090 experiments show that direct
root PUCT remains insufficient, but stage-boundary PUCT succeeds on several
subproblems, including Floor-10 resources and the final captain.  The remaining
failure is stage composition: a locally successful low-gem route can still
consume the yellow-key buffer required by later Floor-8 and Floor-10 resources.
\end{abstract}

\section{Introduction}
Magic Tower differs from many common game benchmarks because its difficulty is
not caused by hidden information, stochasticity, or real-time control.  The
environment is deterministic, fully observable, and compact enough to simulate
exactly.  Its hardness comes from long-horizon resource dependence: a key spent
on an unnecessary door, a potion taken before a shield, or one point of attack
missing at a combat threshold can make a much later state infeasible.  The
project objective is to solve the post-thief first-ten-floor scenario and set
the terminal flag
\[
  \texttt{10f\_captain\_defeated}(s)=1
\]
with positive health under strict replay.  The simplified scenario removes the
Floor-4 shop and flying item, keeps the Floor-6 and Floor-7 key merchants, and
requires the real Floor-10 trap before the skeleton captain can be attacked.

The current result is not yet a fully learned solver.  A prompt-guided
diagnostic route reaches the boss with \(403\) HP and final attributes
\((ATK,DEF)=(27,27)\).  The best self-generated pure route family reaches early
and mid-stage milestones such as the sword and shield, and separate 4090 trials
have reached the first Floor-10 resource, but they still fail from key and HP
bottlenecks.  This motivates a more principled hard-exploration method:
Go-Explore stores stepping-stone states, while PUCT-MCTS performs local planning
from each archived state.  A learned potential from hp403 is allowed only as a
shaping signal and is evaluated separately from the pure no-expert line.

\section{MDP Formulation}
We model the task as a finite-horizon deterministic single-agent MDP
\[
  \mathcal M=(\mathcal S,\mathcal A_{\mathrm{valid}},f,\mathcal G,\mathcal F,H,r).
\]
A state \(s\in\mathcal S\) contains the complete map state of Floors 1--10, the
current floor and coordinate, hero resources \((HP,ATK,DEF,money)\), key counts,
consumed objects, triggered events, and flags.  The valid action set is the set
of currently executable macro-actions:
\[
  a_t \in \mathcal A_{\mathrm{valid}}(s_t).
\]
Each action chooses an interaction node, not an individual arrow key.  The
simulator expands it into a shortest path to a reachable item, stair, event,
merchant, openable door, or killable enemy.  The transition is deterministic:
\[
  s_{t+1}=f(s_t,a_t).
\]
Terminal success is
\[
  \mathcal G=\{s:\mathrm{flag}_{10F\_\mathrm{captain}}(s)=1 \land HP(s)>0\}.
\]
Failures include death, invalid transitions, timeouts, and dead states with no
useful executable actions.  The sparse task reward is
\[
  r_{\mathrm{task}}(s,a,s') =
  R_G\mathbf 1[s'\in\mathcal G]
  -R_F\mathbf 1[s'\in\mathcal F]
  -\kappa,
\]
where \(\kappa\) is a small macro-step cost.  The optimal value satisfies the
single-player Bellman equation
\[
  V^*(s)=
  \max_{a\in\mathcal A_{\mathrm{valid}}(s)}
  \left[r(s,a,f(s,a))+\gamma V^*(f(s,a))\right].
\]
Unlike a two-player zero-sum game, there is no minimax sign flip.  A PUCT-MCTS
rollout therefore backs up
\[
  G_k = r_k+\gamma G_{k+1}
      = \sum_{i=k}^{L-1}\gamma^{i-k}r_i+\gamma^{L-k}\hat V(s_L).
\]

Combat is the main discontinuity.  For a monster \(m\), the damage formula is
\[
  D(s,m)=
  \left\lceil \frac{HP_m}{\max(1,ATK(s)-DEF_m)} \right\rceil
  \max(0,ATK_m-DEF(s)).
\]
Thus a single red or blue gem can reduce future damage by hundreds of HP, while
the same gem may have no effect away from a threshold.  This makes dense reward
design unusually sensitive.

\section{Environment and Macro-Action Abstraction}
The simulator is implemented in Python and uses the extracted HTML5 data as the
truth source.  It supports strict battle damage, item pickup, doors, stair
movement, Floor-6 and Floor-7 merchants, the Floor-8 special door, the Floor-10
trap, and the Floor-10 boss flag.  The visualizer remains a separate validation
tool; core learning code runs through \texttt{src/mota\_env} and
\texttt{src/mota\_solver}.

The current action enumeration first computes the connected open region of the
current floor.  Previously, the implementation reconstructed a full path for
every reachable cell on every state expansion.  Since MCTS expands many states,
this made the system CPU-bound.  The new implementation stores only a BFS
parent map and reconstructs paths lazily for selected semantic actions.  More
formally, let \(R(s)\) be the set of grid cells reachable without passing
through a door, enemy, stair, or NPC.  The BFS stores
\[
  \mathrm{parent}_s(x,y)=(x',y',d)
\]
for each \((x,y)\in R(s)\).  A macro-action is then generated from either a
reachable interactive cell or an adjacent blocker:
\[
  \mathcal A_{\mathrm{valid}}(s)
  =
  \{a_{\mathrm{item}},a_{\mathrm{stair}},a_{\mathrm{event}},a_{\mathrm{npc}},
    a_{\mathrm{door}},a_{\mathrm{enemy}}\}.
\]
The path \(\tau(a)\) is recovered only when an action is emitted or executed.
This preserves the old action set but removes most unused path-list allocations.
Unit tests now verify that the parent-map reachability is equivalent to the
previous path dictionary and that every lazily produced macro-action is
executable under strict simulation.

\section{Why Magic Tower Is Hard}
Magic Tower is close to several established benchmarks but does not reduce to
any one of them.  Compared with AlphaZero-style Go or chess
\citep{silver2017mastering,silver2018general}, every decision layer is a
single-agent max layer, and random play almost never reaches an informative
terminal signal.  Board games always end in a win/loss label; Magic Tower
usually enters a dead end before the boss is observable.

Compared with Sokoban, Magic Tower has irreversible spatial constraints plus
resource variables.  Sokoban deadlocks are mainly geometric.  Magic Tower
deadlocks are often numerical: the agent can legally open a door or kill a
monster but thereby lose a key or health buffer required much later.  Compared
with Montezuma's Revenge and other hard-exploration Atari tasks,
Magic Tower has known symbolic rules, but exploration is blocked by exact
resource thresholds rather than hidden rooms alone; this makes Go-Explore
particularly relevant \citep{ecoffet2019goexplore}.  Compared with NetHack and
MiniHack \citep{kuttler2020nle}, Magic Tower is less stochastic and more fully
observable, but its deterministic damage thresholds create sharper local
discontinuities.

ARC-AGI is also informative.  The original ARC proposal emphasized abstract
reasoning under small training sets \citep{chollet2019measure}; ARC Prize 2024
reported substantial gains from program synthesis and test-time adaptation
\citep{chollet2024arcprize}; ARC-AGI-2 increased the difficulty for frontier
systems \citep{chollet2025arcagi2}; ARC-AGI-3 reframed ARC into interactive
turn-based environments \citep{arcprize2026arcagi3}.  Recent ARC-AGI-3 work
also studies executable Python world models that are checked against observed
transitions before planning \citep{rodionov2026executable}.  Magic Tower
naturally extends this direction: it is an interactive symbolic environment
with explicit state transitions, long-horizon planning, video-renderable
trajectories, textual descriptions, and a large community corpus of demos and
play episodes.  These properties make it a promising benchmark for LLM agents
that must infer rules, plan over resources, and justify actions.

\section{Three Experimental Lines}
\subsection{Line 1: Prompt-Guided Route Discovery}
The first line uses Codex-style prompt-guided exploration as diagnostic route
construction.  This is not counted as an autonomous RL baseline.  It was useful
for finding simulator bugs, validating event logic, and producing a strict
benchmark trajectory.  The current hp403 route defeats the Floor-10 captain with
\[
  HP=403,\quad ATK=27,\quad DEF=27,\quad money=262.
\]
It uses no Floor-4 shop and no flying item.  The route is retained as a
benchmark and for visual replay, not as evidence that the pure RL system has
solved the task.

\subsection{Line 2: Expert-Trajectory Potential Learning}
The hp403 route is too narrow to define the full optimal policy.  Direct
behavior cloning from one route risks overfitting to one key order and one
resource schedule.  We therefore use it only to learn a potential function
\(\Phi_\phi(s)\), following the policy-invariance motivation of
potential-based reward shaping \citep{ng1999policy}.  For a successful trajectory
\(\tau=(s_0,a_0,\ldots,s_T)\), we create progress and ranking labels:
\[
  y_t = t/T,\qquad s_j \succ s_i \quad \text{if } j>i.
\]
The potential loss combines regression, pairwise ranking, and dead-end
separation:
\[
  \mathcal L_\Phi(\phi)=
  \sum_t(\Phi_\phi(s_t)-y_t)^2
  -\alpha\sum_{j>i}\log\sigma(\Phi_\phi(s_j)-\Phi_\phi(s_i))
  -\beta\sum_{(s^+,s^-)}\log\sigma(\Phi_\phi(s^+)-\Phi_\phi(s^-)).
\]
The search reward is then potential-based:
\[
  r_{\mathrm{search}}(s,a,s') =
  r_{\mathrm{task}}(s,a,s')
  +\lambda\left(\gamma\Phi_\phi(s')-\Phi_\phi(s)\right).
\]
This keeps task evaluation separate from shaping.  Final success is always
measured by strict replay and the boss flag, not by shaped reward.

In the current implementation we use a linear potential over hand-audited
semantic factors rather than a free-form neural reward model.  Let
\(c_k(s;g)\) denote the \(k\)-th stage-conditioned component for stage \(g\),
including hero resources, key pressure, reachable resources, blocked resource
pressure, monster damage, marginal damage decrease under \(ATK+1\) or \(DEF+1\),
equipment progress, Floor-10 resource progress, and boss margin.  The learned
potential is
\[
  \Phi_\phi(s,g)=
  \sum_k w_{g,k}c_k(s;g)+\sum_k w^{\mathrm{global}}_k c_k(s;g).
\]
Training examples are generated without asking the model to imitate the expert
action.  At route step \(t\), the simulator enumerates all legal macro-actions
\(\mathcal A_{\mathrm{valid}}(s_t)\).  The hp403 action \(a^E_t\) is treated as
a positive ranking candidate only for the one-step potential difference:
\[
  \Delta_k^E =
  \gamma c_k(f(s_t,a^E_t);g_t)-c_k(s_t;g_t),
\]
and each valid alternative \(a^-\) provides
\[
  \Delta_k^- =
  \gamma c_k(f(s_t,a^-);g_t)-c_k(s_t;g_t).
\]
The ranker optimizes
\[
  \mathcal L_{\mathrm{rank}}
  =
  \sum_{t,a^-}
  \mathrm{softplus}\left(
  -\sum_k w_{g_t,k}(\Delta_k^E-\Delta_k^-)
  \right)
  +\eta\|w\|_2^2.
\]
The output is therefore a stage-conditioned potential, not a policy prior.
The downstream AlphaZero-style and archive-MCTS experiments use hp403 only
through
\[
  r_{\Phi}(s,a,s')=\gamma\Phi_\phi(s',g)-\Phi_\phi(s,g),
\]
which enters single-agent MCTS backups as an edge reward and value-return
target.  No hp403 prefix route, behavior-cloning loss, or expert action prior
is used in the potential-only run.

\subsection{Line 3: Go-Explore Archive with PUCT-MCTS}
The new pure exploration line combines a global archive with local MCTS.  A cell
abstraction maps states to coarse stepping stones:
\[
  \chi(s)=
  (\mathrm{stage},\mathrm{floor},ATK\_b,DEF\_b,key\_b,HP\_b,
   \mathrm{mt10\_progress},\mathrm{boss\_margin}\_b).
\]
The archive stores top-\(K\) non-identical candidates per cell:
\[
  \mathcal B[\chi(s)] =
  \{(s_i,\tau_i,\mathrm{score}_i)\}_{i=1}^K.
\]
At each iteration, a cell is sampled according to novelty, progress, and visit
penalty.  From the archived state \(s_c\), PUCT-MCTS selects a local action:
\[
  a =
  \arg\max_a
  \left[
  Q(s,a)+c_{\mathrm{puct}}P(s,a)
  \frac{\sqrt{\sum_bN(s,b)}}{1+N(s,a)}
  \right].
\]
For the pure line \(P\) is uniform or learned from self-generated search traces,
not from hp403.  In the potential-shaping line, hp403 influences only the
edge reward and leaf value through \(\Phi_\phi\).  The archive score is
lexicographic in success, stage progress, HP, keys, and path length, so a high
shaping score cannot replace strict success.

\section{Current Experiments}
\paragraph{Codex-guided route.}
The diagnostic route reaches the captain and is used to test strict replay,
visualization, no-shop/no-fly constraints, and reward curves.  Figure
\ref{fig:curves} shows that shaped reward increases most strongly around
equipment, gem, red-key, Floor-10, and boss events.  This route family remains
a diagnostic artifact rather than an autonomous RL baseline.  The best strict
route currently synced for visualization reaches the Floor-10 captain with
positive HP and final resources around \((ATK,DEF)=(27,27)\).  It is used to
debug route playback and reward factors, not to make claims about the pure
search line.

\paragraph{Potential-only reward learning.}
The potential-learning run
\texttt{4090\_hp403\_potential\_only\_20260602\_014602} uses hp403 only through
\texttt{scripts/learn\_reward\_from\_hp403.py}.  The learner produced \(1578\)
pairwise action-ranking examples from \(317\) strict replay states.  Under the
learned one-step potential ranking, the hp403 action was top-1 in \(52.1\%\) of
states and top-3 in \(85.8\%\), with mean rank \(2.00\).  This is intentionally
not a perfect imitation signal.  The learned potential is useful as a dense
stage-progress preference, but final evaluation remains strict replay:
\[
  \mathrm{Eval}(\tau)=
  \mathbf 1[\mathrm{flag}_{10F\_\mathrm{captain}}(s_T)=1 \land HP(s_T)>0].
\]

\paragraph{AlphaZero-style policy/value model.}
The latest 4090 run,
\texttt{4090\_stage\_warmstart\_20260603\_192636}, trains graph policy/value
models from multiple successful routes.  This is a separate warm-start line,
not the pure no-expert line.  The network is a Transformer over the fixed
resource-graph state:
\[
  f_\theta(G_s,g)=
  \left(p_\theta(\cdot\mid s,g),v_\theta(s,g)\right),
\]
where \(G_s\) contains hero, item, enemy, door, stair, event, and global tokens,
and \(g\) is the target stage.  We use \(d_{\mathrm{model}}=512\), eight heads,
eight encoder layers, batch size \(96\), Adam learning rate \(1.5\cdot10^{-4}\),
and a policy/value loss
\[
  \mathcal L(\theta)=
  -\pi^\top\log p_\theta(\cdot\mid s,g)
  +0.35\,(G-v_\theta(s,g))^2
  +10^{-4}\|\theta\|_2^2.
\]
Each model checkpoint is approximately \(104\) MB.  Training uses 4090D GPUs;
MCTS evaluation remains CPU-bound because every simulation still performs
state cloning, legal macro-action enumeration, and simulator transitions.

\paragraph{Go-Explore and root archive-MCTS.}
We also evaluated warm-start policy checkpoints inside archive-MCTS with
\texttt{--protocol warmstart\_policy}.  From the initial state, the archive
still failed to solve the task.  The best warm-start archive states were:
\[
\begin{array}{ll}
\texttt{shield}: & MT8,\ HP=233,\ ATK=22,\ DEF=11,\ YK=2,\\
\texttt{mt10\_resources}: & MT5,\ HP=754,\ ATK=20,\ DEF=10,\ YK=1,\ BK=1,\\
\texttt{boss}: & MT5,\ HP=680,\ ATK=21,\ DEF=10,\ YK=1,\ BK=1.
\end{array}
\]
These are better than random exploration but far from a complete route.  The
failure mode is consistent across root PUCT and root archive-MCTS: early-stage
policy priors overvalue immediate combat, door opening, and local floor
progress, while undervaluing the key buffer and shield-before-combat schedule
needed by later floors.

\paragraph{Stage composition failure.}
We then attempted to compose learned stages rather than replaying each original
prefix.  The chain
\[
  \texttt{mid\_gems}\rightarrow \texttt{low\_gems}
\]
succeeded and ended at
\[
  (MT1,\ HP=303,\ ATK=25,\ DEF=24,\ YK=2,\ BK=0).
\]
However, continuing from this generated state into \texttt{mt8\_gems} failed:
\[
  (MT8,\ HP=193,\ ATK=25,\ DEF=24,\ YK=0,\ BK=1).
\]
The route completed a local low-gem objective but spent the yellow-key buffer
required by the next stage.  This is the central open problem at the current
checkpoint.  We therefore started a stronger middle-stage training set with
targets \texttt{lower\_gems}, \texttt{mt8\_hp\_ready}, and
\texttt{pre\_mt10\_buffer}.  These targets make the value function care about
continuation viability rather than only local resource completion.

\paragraph{CPU-bound diagnosis.}
During policy training, all four 4090D GPUs reach high utilization and use
about \(8.7\) GB each.  During PUCT and archive-MCTS, GPU usage falls to roughly
\(645\) MB with near-zero utilization, while each process consumes one CPU core.
This confirms that the bottleneck is not neural inference capacity.  It is the
simulator side: macro-action enumeration, BFS reachability, state cloning, and
per-child legality checks dominate rollout time.  The next engineering step is
to batch graph inference and reduce simulator overhead through transposition
tables, compact consumed-node bitsets, reachability caches keyed by dynamic
blockers, and lazy path recovery.

\section{Next 4090 Experiment}
All heavy experiments now run on the 4090 pod; local execution is limited to
editing, report compilation, route visualization, and light tests.  We keep
three result labels:
\[
  \texttt{pure\_search\_rl},\quad
  \texttt{hp403\_potential},\quad
  \texttt{warmstart\_policy}.
\]
The first label must not use hp403 or other successful routes.  The second may
use hp403 only through \(\Phi_\phi\).  The third may use successful routes to
train a policy/value model, but it is reported as an expert-aided comparison.

The immediate run plan is:
\begin{center}
\resizebox{\linewidth}{!}{%
\begin{tabular}{llll}
\toprule
Stage & Training target & Evaluation & Success criterion\\
\midrule
Middle resources & \texttt{lower\_gems} & PUCT from generated prefix & preserves \(YK\) buffer\\
HP buffer & \texttt{mt8\_hp\_ready} & PUCT from generated prefix & enough HP before Floor 8\\
Pre-10F buffer & \texttt{pre\_mt10\_buffer} & PUCT/archive-MCTS & enough \(YK\) for Floor 10\\
Final suffix & \texttt{mt10\_resources}, \texttt{boss} & strict replay & captain flag true\\
\bottomrule
\end{tabular}
}
\end{center}
The main question is whether a generated state, not a replayed expert prefix,
can be passed from one stage policy to the next:
\[
  s_0 \xrightarrow{\pi_{\mathrm{mid}}}
  s_1 \xrightarrow{\pi_{\mathrm{lower}}}
  s_2 \xrightarrow{\pi_{\mathrm{mt8}}}
  s_3 \xrightarrow{\pi_{\mathrm{mt10}}}
  s_4 \xrightarrow{\pi_{\mathrm{boss}}}
  s_T\in\mathcal G.
\]
If this chain fails because a stage greedily spends keys or HP, the next model
will train on continuation-aware values:
\[
  \tilde G_t =
  G_t
  +\lambda_1\mathbf 1[YK\ge 2]
  +\lambda_2\mathbf 1[HP\ge h_g]
  +\lambda_3\Delta \mathrm{BossMargin}
  -\lambda_4\mathbf 1[\mathrm{dead\_end}].
\]
This is not a replacement for task reward.  It is a training target for
stage-value estimation and archive cell priority.

The CPU-bound engineering plan is also part of the next run.  PUCT currently
performs one network inference per expanded state, but most wall-clock time is
spent before inference.  We will therefore:
\begin{enumerate}
\item cache legal macro-actions by compact dynamic-blocker keys rather than
      full scalar state;
\item represent consumed nodes with bitsets and avoid full floor-grid clones;
\item use a transposition table for repeated MCTS states;
\item batch neural evaluations across leaf states;
\item reconstruct primitive paths only for the final selected macro-action.
\end{enumerate}
The target is not merely higher GPU utilization.  The target is more archive
expansions per hour under strict replay, because the current failure is
insufficient diverse exploration of feasible key schedules.

\section{Future Work: MOTA as an LLM Benchmark}
Magic Tower can be turned into a benchmark suite beyond this first-ten-floor
RL project.  The environment can expose three synchronized interfaces: symbolic
JSON state, natural-language state summaries, and video frames from the
visualizer.  An LLM agent can then be evaluated on action selection,
trajectory-level planning, rule discovery, and post-hoc explanation.  This is
analogous to ARC-AGI's emphasis on test-time reasoning, but Magic Tower adds an
explicit transition function and long interactive trajectories.  The community
already contains many game variants, demos, and complete episodes; these can
support supervised route modeling, offline RL, reward learning, and held-out
map generalization.  A robust benchmark should separate seen maps, unseen maps,
seen rule sets with shuffled layouts, and video-only or text-only observation
conditions.

\section{Limitations}
The current simulator is a first-ten-floor research subset, not a full 50-floor
solver.  Macro-actions hide primitive movement, which is appropriate for
resource planning but not for end-to-end pixel control.  The hp403 route is a
single expert trajectory and therefore insufficient for imitation learning by
itself.  Finally, manual prompt-guided exploration helped diagnose the
environment; the next experiments must keep this diagnostic data separate from
pure search/RL results.

\section{Conclusion}
Magic Tower is best treated as a deterministic long-horizon planning benchmark
with sparse terminal reward and discontinuous resource thresholds.  Pure
AlphaZero-style root search is not enough because useful terminal states are too
rare and early local choices can destroy late resource feasibility.  The newest
4090 experiments sharpen this conclusion: stage-conditioned policy/value models
can solve suffix subproblems from good archive states, but naive composition
still fails when a locally successful stage spends the yellow-key or HP buffer
needed by the next stage.  The next system therefore combines Go-Explore's
archive of stepping stones, continuation-aware stage values, single-agent
PUCT-MCTS backups, and potential-based shaping learned from the hp403 route.
This preserves a clean distinction between pure no-expert search and
